# Личный кабинет курсанта

Репозиторий нашего учебного проекта. Здесь мы разрабатываем личный кабинет по заданию. Чтобы не было хаоса и лишних вопросов, внимательно прочитайте эту инструкцию перед стартом.

---

## Стек технологий

* **PHP:** 8.5 (минимум 8.3)
* **Фреймворк:** Laravel 13
* **База данных:** MySQL или MariaDB (в настройках всегда указываем `mysql`)
* **Менеджер пакетов:** Composer
* **Frontend:** Blade-шаблоны + Tailwind / Alpine.js через CDN

---

## База данных

В корне проекта лежит файл `database.drawio`. 
1. Откройте сайт [draw.io](https://diagrams.net) (`File` -> `Open`) и загрузите этот файл.
2. Там уже описаны базовые таблицы (`users`, `student_profiles` и системные таблицы Laravel).
3. Если вы делаете новый модуль (например, расписание), добавьте свои таблицы в этот же файл с понятными названиями (например, `study_schedule`) и закоммитьте изменения вместе с задачей.

## Как запустить проект у себя

**1. Клонируйте репозиторий и перейдите в папку проекта:**
```bash
git clone <ссылка_на_репозиторий>
cd LK-students
```

**2. Переключитесь на рабочую ветку:**
```bash
git checkout develop
```

**3. Установите зависимости:**
```bash
composer install
```

**4. Создайте файл настроек и сгенерируйте ключ приложения:**
```bash
# Для Windows (cmd):
copy .env.example .env

# Генерация ключа:
php artisan key:generate
```

**5. Настройте подключение к БД:**
Заранее создайте пустую базу данных `lk_students` в phpMyAdmin. Затем откройте файл `.env` и пропишите свои данные для подключения (`DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`).

**6. Накатите миграции (создание таблиц):**
```bash
php artisan migrate
```

**7. Создайте символическую ссылку для хранения файлов (аватарок):**
```bash
php artisan storage:link
```

**8. Запустите локальный сервер:**
```bash
php artisan serve
```
После запуска проект будет доступен по адресу: http://127.0.0.1:8000

## Правила работы (обязательно)

### 1. Работа с ветками
* Ветку `main` **не трогаем вообще**.
* Вся основная работа ведётся вокруг ветки `develop`.
* Под каждую свою задачу создавайте отдельную ветку от `develop`:
  ```bash
  git checkout -b feature/название-задачи
  ```
  *Пример: `feature/canteen-menu`*

### 2. Оформление коммитов
Называйте коммиты понятно, используя стандартные префиксы:
* `feat:` — новая функция *(например: `feat: добавить форму заказа справки`)*
* `fix:` — исправление ошибки *(например: `fix: поправить редирект после логина`)*
* `docs:` — правки в документации или схеме БД

> Коммиты в духе `fix`, `1`, `update`, `сделал` не принимаются.

### 3. Требования к коду
* Пишем на чистом ООП, соблюдая структуру Laravel.
* **Никакого PHP-кода внутри Blade-шаблонов** (используем директивы `@if`, `@foreach` и т.д.).
* Валидацию входящих данных выносим только в **FormRequest** (`php artisan make:request`).
* Запросы к базе делаем через **Eloquent ORM** (`User::where(...)`), без сырого SQL.

* ### Как работать в парах

Так как над каждой задачей работают два человека, вы можете выбрать один из двух форматов взаимодействия. Выбор формата зависит от вашей сработанности и сложности задачи. (если есть идеи по форматам или вопросы - не стесняйтесь)

#### Формат 1: Разделение ролей
Вы работаете **в одной ветке** (`feature/название-задачи`), но четко делите зоны ответственности:
*   **Роль 1:** Продумывает бизнес-логику, структуру базы данных (добавляет таблицы в `database.drawio`), описывает маршруты и правила валидации. Может писать документацию или формы запросов (FormRequest).
*   **Роль 2:** Пишет основной код (Контроллеры, Модели, Blade-шаблоны) на основе того, что спроектировал первый.
*   **Итог:** Вы оба проверяете код локально, делаете общий коммит в вашу ветку, и **только один человек** (или вы вместе) создает Pull Request в `develop`. Это самый безопасный путь, риск конфликтов минимален.

#### Формат 2: Параллельная разработка (Разделение по слоям)
Вы создаете **две отдельные ветки** от `develop` (например, `feature/task-back` и `feature/task-front`), чтобы не мешать друг другу в файлах.
*   **Человек А:** Делает бэкенд (Миграции, Модели, Контроллеры, FormRequest).
*   **Человек Б:** Делает фронтенд (Blade-шаблоны, верстка), опираясь на макеты или договоренности.
*   **Как мержить без боли:** 
    1. Человек А первым делает Pull Request своей ветки в общую ветку задачи.
    2. Человек Б делает `git checkout develop` и `git pull origin develop`, чтобы подтянуть бэкенд к себе. Затем мержит бэкенд в свою ветку, решает конфликты (если есть) и только потом делает свой Pull Request.
    *Внимание:* Если вы не уверены в своих силах, используйте **Формат 1**. **Формат 1** требует максимальной сработанности.

### 4. Проверка перед сдачей
Перед тем как открывать Pull Request в `develop`:
1. Прокликайте руками все страницы и формы, которые вы сделали.
2. Убедитесь, что проходят тесты:
   ```bash
   php artisan test
   ```
